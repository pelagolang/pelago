# `std.crypto`: hashes, MACs, key derivation and (later) ciphers (draft 1, 2026-11-12)

Status: batch 1 is built (see "Order of work"). Everything is written in Pelago itself, with no libc and no
external code, and every algorithm is checked against official vectors or against Python's `hashlib`, `hmac` and
`hashlib.pbkdf2_hmac` (generated by `compiler/std/tests/gen_crypto.py`).

## Scope (Dennis, 2026-11-12)

"It'll have to support all the current hashes in existence." So the goal is the full catalogue below, landed in
batches, most-used first. Not in scope for now: TLS, X.509, certificate parsing (those are a library on top).

## Rules

1. **System randomness only.** Crypto never uses `std.random`'s seeded `rng` (splitmix64). Keys, nonces and salts
   come from the system (`random.bytes`, `getrandom` / `RtlGenRandom` / `getentropy`) or from a CSPRNG seeded from it
   (batch 3).
2. **Constant time where it matters.** No branch and no table index depends on secret data; only `+%`, `*%`,
   rotations and bit operations touch it. Comparing secrets uses `hash.equalConstTime`, never `==`.
3. **One streaming interface** for every hash (below).
4. **Three honest namespaces**, so the name of the module says how far to trust it:
   - *cryptographic*: `std.sha2`, `std.sha3`, `std.blake2`, `std.blake3`, ...
   - *legacy / broken* in `std.legacy` only (MD5, SHA-1, MD4, MD2): kept because file formats, git and old
     protocols still use them. Never use them to protect anything. Every doc line says so.
   - *not cryptographic* in `std.checksum` (CRC, Adler) and `std.fasthash` (xxHash, FNV, Murmur, wyhash, ...): for
     hash tables and error detection, never for security or untrusted input without a keyed variant.
5. **Test vectors first.** A module lands only with the official vectors (NIST CAVP / RFC / reference code) or a
   generated corpus checked against a trusted implementation, plus a streaming test (any chunking gives the same
   digest).

## The shared interface (`std.hash`, built)

```
pub interface hasher {
    fn update(inout self, data: [byte])
    fn finish(self) -> [byte]        // digest of everything fed; does not change the hasher
    fn reset(inout self)
    fn fresh(self) -> Self           // a new hasher of the same kind, for generic code
    fn outputSize(self) -> int
    fn blockSize(self) -> int
}
hash.digest(h, data)  hash.digestText(h, text)  hash.hex(bytes)  hash.fromHex(text)  hash.equalConstTime(a, b)
```

- **Pelago's part.** A hasher is a plain value, so `finish` pads a copy and the hasher stays usable (no "already
  finalised" state to misuse, which is a real bug class in other APIs). `fresh` exists because a generic function
  cannot `copy` a type parameter; it is also what HMAC and PBKDF2 use to start over.
- **Conventional.** `update` / `finish` / `reset` and the hex helpers are the same shape as every other language's
  hash API; we kept the names so the library is familiar.
- Extendable-output functions (SHAKE, BLAKE3, cSHAKE, K12) also implement `hasher` with a default length and add
  `squeeze(n)` for more.
- Keyed hashes (BLAKE2 keyed, BLAKE3 keyed, SipHash, KMAC) are constructed with the key and then are plain hashers.

### Beyond hashes (the order Dennis's coordinator proposed)

ChaCha20, XChaCha20, Poly1305, ChaCha20-Poly1305 and XChaCha20-Poly1305 (batch 3); a ChaCha20 CSPRNG seeded from the
system with automatic reseeding (batch 3); X25519 and Ed25519 (batch 5; the field arithmetic can use 25.5-bit limbs in
`int`, so it does not wait for `int128`); AES with a constant-time bitsliced core (no lookup tables, so no cache-timing
leak), AES-GCM, AES-GCM-SIV (batch 5); P-256 / P-384, RSA, secp256k1 would need `uint256` and wait for the 128-bit
work. Constant-time big arithmetic for those is its own design.

## Order of work

1. **Batch 1 (this PR, built):** `std.hash`, `std.sha2` (all six), `std.mac` (HMAC), `std.kdf` (HKDF, PBKDF2),
   constant-time compare, hex.
2. **Batch 2:** `std.sha3`, `std.blake2`, `std.blake3`, `std.legacy` (MD5, SHA-1), `std.checksum`, `std.fasthash`
   (the most-used of everything left).
3. **Batch 3:** ChaCha20, Poly1305, AEAD, CSPRNG, scrypt, Argon2, bcrypt, PHC strings.
4. **Batch 4:** the rest of the hash catalogue (RIPEMD, SM3, Streebog, Whirlpool, Tiger, K12, MD4, MD2, the rest of
   `std.fasthash`).
5. **Batch 5:** X25519, Ed25519, AES and its modes.

Each batch is one PR, tested, and followed by a website update checked on the live site.

## What is conventional, what is Pelago's

- **Conventional (on purpose):** the algorithms themselves, their parameter names and test vectors. Nobody should
  invent a hash. Names follow the standards (`sha256`, `hmac`, `hkdf`) so people can find them.
- **Pelago's own:** the value-semantics hasher (`finish` on a copy, `fresh`, no finalised state), one interface
  for every hash and a generic `digest`, the three-namespace split with `std.legacy` as a visible label, `?` and
  `result` instead of error codes for parse failures, and (planned) `sink` receivers so a key is consumed by the
  call that uses it and zeroed afterwards with `deinit`.

## Known limits and plans (honest list)

- **Speed is not measured yet.** Today the message schedule is a fresh `[uint32]` per block and the input is a `[byte]`
  list, so a block costs allocation that C's stack array does not. The standing rule applies: if a benchmark
  comes out worse than C or Rust, there will be a plan to lower it. First candidates: fixed-size array locals for the
  schedule, `unrolled` rounds, and intrinsics (rotate, SHA-NI / ARM crypto extensions) behind the same API.
  No benchmark has been run for this batch (benchmarks only run when asked).
- **Register-poor targets:** SHA-256 is 32-bit words only, so it is the right default on microcontrollers; SHA-512 and
  BLAKE2b need 64-bit words and cost about twice on 32-bit cores. The numbers will be reported when the benchmark
  harness gets a crypto set.
- **PBKDF2 recomputes the key block** each round (two extra compressions per round, about 2x the optimum) because a
  generic hasher cannot be copied. Fix: a `clone`-able hasher supertrait or a state snapshot in `hasher`.
- **Constant time is by construction, not proven.** The compiler may in principle turn a bit trick into a branch. A
  checker attribute (`@ct`, rejecting secret-dependent branches and indexing) is a candidate card.
- **Found while building (compiler bugs, not fixed here):** `var x = h` of a read-only generic parameter compiles
  and then frees twice at runtime (a read-only parameter of a concrete type is correctly rejected); an associated
  function of a generic struct (`hmac<H>.new(h, key)`) fails to unify `H` with itself, so the constructor is a free
  function; `uint64` values with the top bit set print as negative numbers; `uint64` has no `wrapToByte`
  (we narrow through `rtCast<uint64, int>`).
