# Benchmark suite maturity plan (proposal, no code written)

## 1. What goose does that we don't

Source: aardappel/goose `bench/` (design.md, run_bench.py, results.md, notes.md) and our `compiler/benches`.

| Area | goose | Pelago today |
|---|---|---|
| Question asked | "Does the data-structure/memory strategy win?" 16 programs chosen per language-design axis (control, pointer-rich, growth, weak spots such as lru, blur) | 16 kernels, mostly scalar loops and small collections. Good for codegen, thin on allocation, strings, trees, records |
| Comparison tiers | idiomatic C++, expert C++, safe Rust (second Rust row only for a semantic reason), allocator tiers (malloc, mimalloc, arena) | one C twin, one Rust twin |
| Compilers | MSVC and clang, same source, same flags; one headline per toolchain | gcc only (clang on ARM macOS/Windows), rustc |
| Sizes | 3 data sizes (cache-resident, medium, beyond cache) | 1 size, most programs run 5-50 ms, so noise is 20% or more |
| Metrics | wall time, peak memory (and payload vs RSS), startup floor, JIT vs compiled | wall time only |
| Method | best of 3 after 2 warm-ups, core pinning, checksum check across all implementations, whole-process timing stated up front | best of N, output equality check against the C twin |
| Results page | generated by the harness ("do not edit by hand"), reading guide, environment table with pinned versions, one "across all benchmarks" table with geomean, one section per program with commentary, caveats section | `arm-timings.md` written by hand, `website/content/bench.json` (one machine, one run, three numbers per row) |
| Honesty tooling | A/B scripts (bounds-check elimination on/off), notes on which rows are not like-for-like, noise thresholds (10-15%) | `--checked` column (a good idea goose lacks: C -ftrapv and Rust overflow-checks) |
| Compile time | none in the excerpt I read | none |

Things we already do better: exact-overflow-trap comparison (`--checked`), three OS plus ARM CI, a machine-readable `--json`.

## 2. Target structure

**Layout**
```
bench/
  design.md          why each program exists, fairness rules
  programs/<name>/{pelago.pel, c.c, cpp.cpp, rs.rs, expected.txt, sizes.toml}
  harness/run.py     builds, verifies, times, writes results
  toolchains.toml    pinned versions (see below)
  results/<date>-<machine>.json   raw data, committed
  results.md         generated, never hand edited
```
`compare.sh` stays as the quick local entry point, calling the same harness.

**Programs (grow from 16 to about 30, in three groups)**
1. Kernels (what we have): collatz, divmod, fib, tak, sieve, floatloop, loop_sum...
2. Data-structure programs, goose style: binary trees (alloc), strings and word counts (hash map), records/struct lists, sort, an interpreter/AST walk, a result/option error path, graph BFS, LRU (our weak spot, include on purpose), matrix/blur (vectoriser).
3. Whole-program: a lexer/parser run (our own compiler's lexer rewritten in Pelago is the long-term "self-hosting" benchmark).
Each program: 3 sizes (small fits L2, medium fits L3, large does not), a checksum line, the same checksum in every language.

**Languages and tiers**
- C: gcc `-O2` (the goal), gcc `-O0`, gcc `-O2 -ftrapv` (checked), clang `-O2`, and tcc (see 3).
- C++: g++ `-O2` and clang++ `-O2`, two tiers like goose: idiomatic (vector, string, unordered_map, unique_ptr) and expert (flat arrays, arena). Honest note: for scalar kernels C++ compiles to the same code as C, so the C++ rows only differ where the library matters (strings, maps, trees). That is where they are worth having. C++ is not generally faster than C; the same compiler backend runs both.
- Rust: `-O` (and `-C codegen-units=1` as goose does), plus `overflow-checks=on`.
- Pelago: `--opt`, plus `--no-opt` as a trend line.
Standing target stays: every row at or below gcc -O2 and Rust -O, with exact overflow traps on.

**Metrics per cell**
run time (median and min of N, plus spread: MAD or min/max), compile time (see 3), binary size (stripped), peak RSS (`/usr/bin/time -v` or `wait4` rusage on Linux, `GetProcessMemoryInfo` on Windows), startup floor (empty program, since we are static with no libc, ours should be very low and is worth showing).

**Method rules**
- 3 discarded warm-ups, then at least 7 runs; report median and min, flag a row noisy if spread exceeds 10%. Shared CI runners are noisy, so CI numbers are for trends and the committed headline run comes from a quiet machine with `taskset -c` pinning and the governor fixed.
- Whole-process wall clock for the headline plus in-program timing for kernels, stated in the reading guide.
- Compilers pinned: build a container image (Ubuntu 24.04 digest) with exact gcc, g++, clang, tcc, rustc versions; record versions in the results header. ARM runners record theirs automatically.
- Checksum comparison across every language before any time is accepted (already done against C; extend to C++ and Rust).

**Results page (generated)**: reading guide, environment table, "across all benchmarks" table (ratio vs each baseline, geomean, count at or below), per-program sections with a table and one commentary sentence, compile-time table, binary-size and memory table, caveats. Same JSON feeds `website/content/bench.json` so the site and the repo cannot disagree. History file keeps one line per week so the site can draw a trend.

## 3. gcc, tcc, and compile time

tcc compiles about 10x faster than gcc but emits roughly `-O0`-quality code (no real optimiser, no register allocation across statements). Show it honestly as a different axis, not a rival on run time:
- Two tables: **run time** (tcc row will sit near gcc -O0, often 2-5x slower than -O2) and **compile time** (cold, whole program: source to runnable executable, median of 7, including link).
- One combined view, "time to first result": compile time plus one run, per program and size, plus a break-even line: how many runs until gcc -O2 beats tcc. Pelago's pitch is that it should be near tcc on compile time and near gcc -O2 on run time, so this chart is the strongest we can make. Needs us to measure `pelago build` honestly (it has no assembler or linker step, so it should do well, but we must publish the number, whatever it is).
- tcc caveats: x86-64 and AArch64 Linux are supported, Windows tcc is x86-64 only and macOS tcc is poor, so tcc is Linux (x86-64 and ARM) only. tcc has no `-ftrapv`, so it has no checked row.
- Also add `pelago build --no-opt` vs `--opt` compile times, and `pelago run` (interpreter) start time.
