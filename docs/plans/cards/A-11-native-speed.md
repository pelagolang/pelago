Title: Native speed: from 4.5 times slower than C at -O2 towards 1.5 to 2 times
Column: Doing
Work items: [a11-work-items.md](../a11-work-items.md) (the open work, split for parallel threads)
Order: after A-09 N6 (track A)
Depends on: A-09; A-04 (the IR optimiser)
Size: XL, in stages (S1 to S6), each measured
Touches: `compiler/src/native/` (instruction selection, register assignment), `compiler/src/ir/opt/` (new passes), `docs/design/backend.md`

# Where we are

On the collatz-and-`fib(35)` program: interpreter about 7 s, native with registers and the optimiser 0.45 s, C `-O0` 0.23 s, C `-O2` 0.10 s (`docs/design/backend.md`, section 6).
We are about twice C at `-O0` and 4.5 times C at `-O2`. Two groups of causes: what the *language* asks for, and what our *backend* does badly.

# What costs time, biggest first

| # | Cause | Kind | What fixes it |
|---|---|---|---|
| 1 | **Division and remainder by constants.** `x % 2`, `x / 2` run `idiv` (20 to 40 cycles) plus our zero and `-1` checks. C turns them into a shift or a multiply. | backend + optimiser | S1: the optimiser rewrites `x / 2^k`, `x % 2^k`, and division by other constants into shifts/multiplies (the "magic number" method); signed forms need the usual correction. Constant divisor also removes the zero and `-1` checks. |
| 2 | **Checked arithmetic.** Every `+ - *` is followed by `jo`/`jc`. C has no checks. | language decision | S2: range analysis in the optimiser (a loop counter bounded by its compare cannot overflow; `i + 1` after `i < n`), merging checks, moving them out of loops. Keep the checks that matter; `+%` etc. stay free. This is the cost of safe arithmetic and should not be removed wholesale. |
| 3 | **Values in memory.** Only five callee-saved registers, one per value for its whole life, no splitting; every other value costs a load and a store per use; every operation is `ld rax; ld rcx; op; st`. | backend | S3: real linear-scan register allocation with live-range splitting, all registers (caller-saved ones for values not live across calls), two-address instructions working directly on registers, compare-and-branch fused (`cmp` + `jcc`, no `setcc`/`test`), addressing modes (`[base + index*8 + disp]`), constants as immediates. This needs a machine-level IR between the IR and the bytes (see A-10, option 2). |
| 4 | **Calls.** Frame setup, saving callee-saved registers, passing everything through memory, no inlining of small functions unless `--opt` is on. | backend + optimiser | S4: `build` uses the optimiser by default; inlining thresholds tuned on the benches; leaf functions without a frame pointer; arguments stay in registers. |
| 5 | **Slots zeroed on every execution** (an interpreter rule), reused memory zeroed on `alloc`. | backend + IR | S5: drop the rule where the lowering writes before reading (the verifier or lowering can say which slots need it); promote slots to values (A-04 already does much of this, extend it); inline the allocator's fast path. |
| 6 | **Small copies and fills** use `rep movsb`/`rep stosb` (a fixed start-up cost of ten or more cycles). | backend | S5: constant sizes up to 64 bytes become a few `mov`s. |
| 7 | **Loops**: no invariant hoisting, no unrolling, no alignment of loop heads. | optimiser | S6: loop-invariant code motion, strength reduction (`i * 8` to an add), loop alignment, branch layout (likely path falls through). |

# Method

Measure first, change one thing, measure again. `compiler/benches/` gets a few more programs (the collatz/`fib` pair, a list sum, a string builder, a map workload, a struct-heavy loop, a recursion test) and a script prints the table "interpreter / native / C -O0 / C -O2" with the same algorithm in C. Every change is covered by the existing three-way tests, plus new tests for each optimiser pass (before and after must print the same, with the edge cases of `backend.md` section 2).

# Expectations (honest)

S1 alone should remove a big share of the collatz time. S1 to S3 together should reach about 1.5 to 2 times C `-O2` on integer code; matching C needs inlining heuristics, vectorisation and more, which belong to ROADMAP Phase 6. Float-heavy code is another matter: today every float lives in memory, so it gains the most from S3.

# Questions for the owner

1. Order S1 (constants), S2 (checks), S3 (registers)? Recommended: yes, S1 first because it is small and visible.
2. Keep overflow checks on in release builds (recommended; a flag may turn them off later, with the checks themselves optimised first)?
3. Introduce the machine-level IR with S3 (recommended)?

# Progress

**S1, part 1 (done): powers of two.** `ir/opt/divconst.rs` rewrites `x / 2^k` and `x % 2^k` (signed and unsigned) into shifts and masks, with the usual bias for negative dividends, and `x % 2^k == 0` (or `!= 0`) into `x & (2^k - 1)` compared with zero. Tests compare before and after for `i8`, `i32` and `i64` at the edges. On `compiler/benches/collatz.pel` (steps for 1 to 300,000): native `--opt` 0.30 s before, 0.23 s after; C `-O0` 0.15 s, C `-O2` 0.07 s on this container.

**S1, part 2 (done): other constant divisors.** New IR operations `MulHi`/`UMulHi` (the high half of the full product, integers up to 64 bits) in the IR, verifier, interpreter and x86 generator (`imul`/`mul` one-operand form, or a 64-bit multiply and a shift for narrow types). `divconst.rs` rewrites `x / c` and `x % c` for any constant `c` with the magic numbers of Granlund and Montgomery (unsigned, with the add-and-shift form when the multiplier needs one more bit) and Hacker's Delight (signed); a remainder is `x - (x / c) * c`. Left alone: 0, 1, -1 and negative powers of two (`MIN / -1` still wraps, zero still stops). Tests: the magic plans are checked exhaustively for 8 bits and at the edges for 16, 32 and 64; whole-IR differential tests for `i8` to `i64`; native three-way tests with loops. New bench `compiler/benches/divmod.pel` (digit sums, `% 3`, `/ 7` over 3,000,000 numbers): native `--opt` 0.45 s before, 0.086 s after; C `-O2` 0.041 s.

**S3, first round (done): the generator stops wasting moves.** Constants are immediates (no register, no frame slot); a comparison that only feeds the branch ending its block is not stored (`cmp` + `jcc`), and a jump to the next block falls through; operands are used from their own registers and results are built in place; `r10` and `r11` hold values that are not live across a call. Still open from S3: real linear scan with live-range splitting, all caller-saved registers, addressing modes, a machine-level IR (needed for A-10 option 2).

**S2, first round (done): checks that cannot fire.** `ir/opt/ranges.rs` finds values known to be small and non-negative (a widened byte, `x & 255`, `x % 10`, `x >> 3`, sums and products of those) and turns a checked `add`, `sub` or `mul` that provably fits into the plain operation. It does not look through loops: block parameters and loads have no range, so a loop counter's `+ 1` keeps its check unless the lowering already emitted a plain add (as it does for `for i in 0..n`). Next for S2: induction variables (a counter that starts at a constant, goes up by 1 and is bounded by a dominating compare).

**S2, second round (done): loops.** `ir/opt/ranges.rs` now gives block parameters the join of what their edges pass (repeated to a fixed point, widening after a few steps), and cuts a range with the comparison that guards the block: a block entered only by one side of `branch (lt i, n)` knows `i < n` in everything it dominates (`ir/opt/dom.rs`). So `while i < n { i += 1 }` loses its check; `i += 2`, `i <= n`, and a counter nothing bounds keep theirs. Signed counters only for now: an unsigned `i < n` with unknown `n` bounds `i` by `u64::MAX`, which the shared signed/unsigned range cannot hold. Across `examples/programs` and the benches the optimised IR has 407 checked operations instead of 493.

**Loops (W9, done in part): `ir/opt/licm.rs`, `ir/opt/layout.rs`, `ir/opt/loops.rs`.** Loop-invariant code motion moves arithmetic, compares, casts and address arithmetic that cannot stop in front of the loop (a load too when the loop writes no memory and the load is in the header or reads a slot of the function; division never, since the loop may run zero times). Layout puts a loop's body first and its header last, so an iteration ends in one conditional jump back instead of a conditional jump out plus a jump back, and moves blocks that only `stop` to the end. Measured with `compare.sh` (best of 7): loop_sum 0.68 s to 0.39 s, sieve 0.26 s to 0.19 s, mapwork 0.053 s to 0.043 s, the rest within noise. Not done: strength reduction (`i * 8` into an add) because it fights the addressing modes planned in W5, which absorb the scale; aligning loop heads needs `Asm::align` in the generator (collatz moves between 0.12 s and 0.14 s when unrelated code shifts it, so this is worth doing).

**Structs in registers (SROA).** `ir/opt/split.rs` now splits two slots that are copied whole into each other (`p = p.add(d)` copies a temporary into `p`): both get the same pieces and the copy becomes a load and a store per piece, which `promote` then turns into block parameters. `ir/opt/ranges.rs` narrows after widening, so `x = (x + 3) & 65535` in a loop keeps a small range instead of `MAX`. structloop: 0.49 s to 0.019 s (C -O2 0.011 s).

Measured with `compiler/benches/compare.sh` (best of 7, this container):

| Program | before (S1) | now | C -O0 | C -O2 |
|---|---|---|---|---|
| collatz, 1 to 300,000 | 0.23 s | 0.09 s | 0.14 s | 0.07 s |
| fib(38) | 0.36 s | 0.30 s | 0.34 s | 0.08 s |

**S4, first part (done): `build` optimises by default.** `pelago build` and `pelago run --native` run the optimiser unless `--no-opt` is given (`--opt` is still accepted and does nothing there); `pelago run` and `pelago ir` stay unoptimised unless `--opt`. The inliner threshold (`SMALL` in `ir/opt/inline.rs`) was tried at 15, 40 and 100 on the ten benches: all differences were within run-to-run noise, so it stays at 40. Leaf functions without a frame pointer and arguments kept in registers are generator work (`native/gen.rs`) and wait for the backend thread.

**S3, second round (done): a real allocator.** `native/regs.rs` now builds live ranges with holes, uses all the caller-saved registers (`r10 r11 r8 r9 rsi rdi`) for values not live across a call, splits the others around calls (store before, load after) when that is cheaper than a callee-saved register or memory, and prefers the register a related value or an argument slot already has. `gen.rs` makes every multi-register shuffle (call arguments, entry parameters, jump arguments, `memcopy`, `print`) one parallel move, lets a result take the register of an operand that dies, drops writes to values nothing reads, and keeps the copies of the side of a branch it does not fall into out of line. Tests run every program with 1, 2 and 4 registers of each kind as well (`gen::REG_LIMIT`). Measured (best of 7, native, this container, before then after): fib(38) 0.36 to 0.28 s, loop_sum 0.77 to 0.33 s, sieve 0.16 to 0.14 s; collatz and tak move by about 10 % either way with where the code lands (see below). Still open from S3: addressing modes, floats in registers, a machine-level IR, shrink-wrapping of the callee-saved saves (`tak` pays them on its base-case path), and branch alignment: the hot loop of collatz changes by 0.09 to 0.13 s just by moving it a few bytes, the Intel jump-crossing-a-32-byte-boundary erratum.

**S3, third round (done): memory operations (W5).** Pointers into frame objects are frame offsets; `ptradd` of a constant or a scaled index folds into the `[base + index*scale + disp]` of the load or store; a `memcopy` of up to 64 bytes is plain 8-byte moves; a `Slot` is cleared only when its block does not overwrite it first. `structloop` went from 0.65 s to 0.08 s (C `-O0` 0.10 s, `-O2` 0.011 s: the rest is that C keeps the struct in registers, which needs the optimiser to split structs into fields), `sieve` from 0.14 to 0.11 s.

**S3, fourth round (done): floats in SSE registers (W11).** `native/regs.rs` allocates floats in `xmm2` to `xmm15` with the same priorities and splitting around calls as the integer registers (no SSE register is callee-saved); `gen.rs` does arithmetic, compares, negation, casts, loads, stores, arguments and results directly on them, and fuses `<`, `<=`, `>`, `>=` with the branch. `floatloop` 0.36 s to 0.13 s (C `-O0` 0.23 s, `-O2` 0.15 s). Details in `docs/design/backend.md` section 6.

**Growing buffers (list_sum, strbuild).** Pushing 5,000,000 integers took 0.08 s against 0.023 s for C, and the C program with `malloc` + `memcpy` + `free` instead of `realloc` takes 0.07 s: all of the gap was copying big buffers and faulting in fresh pages at every doubling. New IR operation `realloc` (null allocates; the first bytes are kept, the rest is zero; the old address is dead) and runtime routine `rt_realloc`: a large block is moved with `mremap` on Linux, so nothing is copied and the pages stay; smaller blocks and Windows allocate, copy and free. `rt_grow` in `core.pel` is now a small check that every push loop inlines; the work is in `rt_grow_slow`, which the inliner never inlines (name suffix `_slow`). list_sum 0.082 s to 0.037 s, strbuild 0.012 s to 0.007 s.

**Common subexpressions and cheaper division (divmod).** New pass `ir/opt/cse.rs`: an arithmetic, compare, negate or cast operation computed again on the same operands under a dominating copy reuses the earlier result (equal constants count as one operand; `ptradd` and the `mul`/`shl` that scale an index are left to the generator's addressing modes). `n % 10` and `n / 10` now share their high multiply. `ranges.rs` turns a signed `/` or `%` by a positive constant into the unsigned form when the dividend is known non-negative, and `divconst` runs after inlining (a callee's `n / 10` is only known non-negative once it sits in the caller's loop), so the sign fix-up disappears. In `gen.rs`, shifts by a constant are built in the result's register, and a multiply by a constant is `imul d, a, imm`. divmod: 0.074 s to 0.033 s (C -O2 0.032 s, Rust 0.038 s).

**List headers in registers, bounds checks, huge pages.** New pass `ir/opt/cache.rs`: a slot of at most 32 bytes whose address only goes to calls that do not keep it (an escape analysis over the module) is read and written through a private copy that promotion turns into registers; the copy is written back before and read again after each such call, so the push loop keeps `len` and `cap` in registers and only the rare `rt_grow_slow` sees the real header. `ranges.rs` decides `i >=u n` / `i <u n` right after the guard `i < n` when `i` is not negative (the bounds check of `for i in 0..xs.len() { xs[i] }`). `rt.rs` asks for transparent huge pages (`madvise`, Linux) for mappings of 4 MiB and more: a 40 MB buffer then takes a few page faults instead of ten thousand. list_sum 0.037 s to 0.024 s (C -O2 0.031 s), strbuild 0.007 s to 0.006 s.

Safety of the slot cache and the huge pages: the escape analysis in `ir/opt/cache.rs` is a whitelist (anything it does not positively recognise counts as keeping the address); `a_slot_given_to_calls_is_cached_unless_a_callee_keeps_its_address` covers a callee that stores the address, casts it to an integer, returns it, passes it to a second callee that stores it, and a call through a function address. `madvise(MADV_HUGEPAGE)` is only asked for mappings of 4 MiB and more, so small buffers keep ordinary pages; where transparent huge pages are off it does nothing, and Windows never calls it.

Windows growth in place: a large block of 1 MiB or more reserves eight times its size with `VirtualAlloc(MEM_RESERVE)` and commits the pages it uses; `rt_realloc` commits the extra pages at the same base (they arrive zeroed), so nothing is copied or moved until the reservation is used up, when it falls back to allocate, copy and free. The reserved length sits above the class byte in header word 0; word 1 stays the committed length. Only the Windows CI job runs this path.

**If-conversion (collatz).** New pass `ir/opt/ifconv.rs` and IR operations `select` and `checked_if`: a branch whose sides only compute a few values becomes straight-line code with conditional moves, which the processor cannot mispredict; the checked arithmetic on a side stops only when that side is the one taken, through an out-of-line test. `lea` replaces `imul` for 3, 5 and 9. `collatz` went from 0.080 s (1.22x C -O2) to 0.064 s (0.96x). See `docs/design/ir.md` and `backend.md`.

PRs: #7 (S1, powers of two), #8 (S2 and S3, first rounds). The open work, with files and dependencies for each item, is in [a11-work-items.md](../a11-work-items.md).

**Tail calls.** `ir/opt/tailrec.rs` turns `return f(args)` inside `f` (also through the join block of an `if`) into a jump to a new loop header made from the old entry block, unless the call is handed the address of one of the frame's slots. tak: 0.29 s to 0.21 s (C -O2 0.18 s). Accumulator-style recursion: in `return x + f(args)` the addition moves into a loop-carried accumulator (starting at 0, added to every other return), so `fib` keeps only its first call; fib38 0.30 s to 0.21 s (C -O2 0.11 s, Rust 0.13 s). Only `+` is handled. Regrouping a *signed checked* sum could move the stop when the terms have mixed signs, so the loop keeps Pelago's exact overflow with one test per term, `(x | (acc + x)) < 0`: a negative term or a wrapped sum sets the sign bit, and the collected sum is never negative. With such a prefix `prefix + t` stops exactly when the original order does, whatever the value `t` of the rest is (a non-negative `t` makes the partial sums grow, so one overflows iff the total does; a negative `t` keeps them between `t` and the prefix), so the base case just adds. The first term that fails the test leaves the loop through a cold block that makes the call as an ordinary call and adds `prefix + (x + result)` with checked additions, as the original did from there on. No copy of the function and no purity analysis are needed, because the additions are the only thing that can stop and they come last. Unsigned and wrapping sums need no test. Tests run every mix of signs in `i8` with and without the pipeline.

**Call setup.** `ir/opt/layout.rs` puts the successor that stays in the loop first and the exits of guards in the body (like the slow path of the accumulator) at the end, so the loop test is one conditional jump back and its exit falls through. `native/gen.rs`: a function whose frame would hold nothing but saved registers (no spilled values, slots or float scratch) pushes and pops them instead of building an `rbp` frame, and values waiting across a call are pushed around it (padded to keep the stack 16-byte aligned); fib's prologue is now two pushes and a pad. fib38 0.24 s to 0.19 s, tak 0.21 s to 0.18 s (best of 15, noisy machine; C -O2 0.12 and 0.17).

**Recursive inlining.** `inline::recursive_once` copies a small self-recursive function (cost at most 120) into itself at up to three of its own calls that do not end the function (a call whose result is returned straight away is a tail call or the slow path of a guard, and stays). It runs after the tail-call pass and before the per-function passes, so the copy sees real arguments. Half the calls of `fib` disappear and the three nested calls of `tak` get cheaper: fib38 0.24 s to 0.13 s (C -O2 0.12 s, Rust 0.13 s), tak 0.20 s to 0.18 s (C 0.18 s, Rust 0.22 s).

**Base-case peeling and a size budget.** `ir/opt/peel.rs` reads the entry test of a recursive function off its first block (a pure test of the parameters that returns a parameter or a constant on one side, as in `fib`'s `n < 2` and `tak`'s `y < x`) and repeats it at the function's own calls that do not end the function: `f(a)` becomes `if test(a) { value } else { f(a) }`, so a call with real work to do is the only one that saves registers. Recursive inlining now needs two or more self calls in the original (a tree of calls; a linear recursion gains nothing from a copy) and may grow the function by at most 200 cost units. tak 0.125 s to 0.075 s of CPU time (C -O2 0.12 s, Rust 0.14 s); fib is about 3 percent faster; the tak function grows from 560 to 784 bytes, fib stays at 288. `compare.sh --checked` adds a table against `gcc -O2 -ftrapv` and `rustc -O -C overflow-checks=on`, which stop on overflow like Pelago and are the fair comparison for fib: Pelago 0.12 s, C 0.15 s, Rust 0.17 s. gcc -O2 without checks unrolls fib about seven levels using wrapping arithmetic (0.06 s); two and three extra levels of inlining made ours slower (register pressure), so the plain -O2 gap on fib stays at about 1.5x to 2x.

**Cheaper accumulator guard.** The signed accumulator carries the room left, `MAX - sum`, instead of the sum. A term fits when it is not above the room as an unsigned number (a negative term is a huge unsigned number, so it fails too), and the next room is `room - term`: one compare-and-branch and one subtraction per term, where the sign-bit test needed a move, an add, a move, an or, a compare and a branch. The exits compute `MAX - room` once. fib38 0.103 s to 0.071 s of CPU time (C -O2 0.061 s, Rust 0.124 s).

**Sieve: three things that were not the loops.** (1) `ir/opt/fill.rs`: a big slot (4096 bytes or more) that the very next loop fills completely (`[x; n]`: a counter from 0, one store per step of exactly the element size, `n * size` equal to the slot) is not cleared first; every other use of it must lie after the loop's exit. The 40 MB array of the sieve was written twice. (2) `native/gen.rs`: the stack probes of a big frame are a loop (`r10`, `r11`) once there are more than eight pages; the sieve's executable went from 95,120 to 5,008 bytes. (3) `ranges.rs` also decides unsigned compares (`i >=u len`) whose two sides have known ranges, which removes the index tests in `while j <= n { flags[j] = 0; j += i }` and in the outer loop. The allocator (`regs.rs`) now prefers the register that most related values already have, so `room - x` that feeds a loop parameter is computed in place (fib loses the four moves around the room update; no measurable speed change, size unchanged). sieve: CPU time best of 25 equal to C -O2 (0.170 s each), median 0.181 s against 0.180 s (before: 0.190 s); Rust -O 0.180 s. What is left in sieve is the 40 MB it has to touch: the C twin's `malloc` fill is vectorised, ours is one store per element (about 4 ms).

**Identities and cold calls.** `cse` now drops arithmetic identities (`x+0`, `x*1`, `x/1`, `x|0`, `x^0`, shifts by 0) for plain and checked operations, which shortens loops such as `structloop` by an instruction. The register allocator weights a call to a cold function (name ending in `_slow`, such as `rt_grow_slow`) as one, so values that live across it stay in caller-saved registers and are saved around the rare call instead of spilling to the stack on the hot path. `strbuild` reaches parity with gcc -O2 this way.

**Fill loops are `rep stos`.** `fill_loops` (in `ir/opt/fill.rs`) finds the loop `[x; n]` makes (a counter from 0, one store of a value that does not depend on it, per step the element size, a constant count, entered by one plain jump) and `native/gen.rs` stores the memory with `rep stosb/w/d/q` from the block that enters the loop; the header and body are not generated. Only loops of 512 bytes or more: the instruction starts slowly. A cache-resident fill is the gain (an array of 1,024 integers made 300,000 times: 0.195 s to 0.018 s of CPU time, C -O2 0.050 s). The 40 MB array of sieve does not gain, because it is bound by page faults, not stores (init alone: 0.041 s to 0.035 s, C 0.030 s; the whole sieve stays level with C -O2). Copy loops are not recognised: array and list copies are already `memcopy` (plain moves up to 64 bytes, `rep movsb` above).

**Masks nobody reads and counters that move together.** `opt/demand.rs` finds, for every integer value, the bits a later use can tell apart (`x & 1023` reads ten bits, a sum reads the bits up to its highest demanded one, a comparison, store, call or checked operation reads all of them, and a loop's block parameters carry the answer around) and drops `x & c` when only bits inside `c` are read. `opt/ivopt.rs` then turns a formula over two or more counters (`x += 3`, `y += 1`, `3 * x + y`) into one counter that starts from the formula on the entry values and steps by the combined step, when nothing else reads the old counters; `dce` now drops block parameters that feed only themselves. Only wrapping operations are followed, so no trap moves. `structloop` goes from 0.011 s to 0.007 s (C -O2 0.011 s, Rust -O 0.005 s, which also runs four iterations per pass in SSE2: that is a vectoriser and stays open).

**Huge pages on our own stack.** The sieve's 40 MB array is a local, so it lives on the program's own 1 GiB stack, which did not get the huge-page hint that heap mappings of 4 MiB and more get. `_start` now calls `madvise(stack, 1 GiB, MADV_HUGEPAGE)` (Linux only, a hint). Page-fault (`sys`) time of the sieve halves (0.027 s to 0.014 s) and its CPU time drops from 0.177 s to 0.151 s (best of 15; C -O2 0.160 s). No other benchmark moved beyond noise, and a recursion a million frames deep still runs.

**Unrolling and counter chains instead of a vectoriser.** Reading Rust's code for `structloop` suggested SIMD, but an eight-way hand-unrolled copy of our own loop already ran at 0.005 s, Rust's time, with no vector code. `opt/unroll.rs` does that in the compiler, once per function after inlining: a two-block loop that tests one counter against a constant bound of at least 256 passes (`i < n`, `i += s`), with a small body and no calls, allocation or stores, runs `K` (2, 4 or 8) copies per pass of a main loop whose test is `i < n - (K-1)*s` (made once, with a `select` that skips the main loop if the subtraction would wrap), and the original loop finishes the rest. The copies run in the original order with the original checked operations, so every trap happens in the same pass. A small cost model keeps it to loops that are bound by their instructions: it compares the longest chain through the loop-carried values (a float sum, a multiplication chain) with the instruction count at about 3.3 per cycle, and unrolls only when `K` copies are estimated at 0.65x the time or less. `ivopt` now also rewrites values that are a counter plus a constant as `counter + constant` directly instead of a chain of additions. Of the eleven benchmarks only `structloop` is unrolled (0.007 s -> 0.005 s); its code grows by 288 bytes, and the other binaries are byte for byte the same size. A vectoriser stays an option for loops that unrolling cannot help (a chain of independent lanes), and costs vector IR, SSE2 encodings and overflow-exact vector checks.

**Literals copied as constants.** `s + "ab"` copied two bytes out of the literal: the address of the data in a register, a load, a store. `opt/constdata.rs` turns a `memcopy` of 1, 2, 4 or 8 bytes from static data into a store of one integer constant (sign extended, as the interpreter reads it), so the address drops out of the loop. strbuild: 36.1M to 32.1M instructions, the binary 4 KB smaller; the time stays dominated by page faults and is about 1.1x C -O2 (Pelago starts 0.9 ms faster than a dynamically linked C program, so the loop itself is further behind than the table shows). What is left in its loop is register copies around the two overflow-checked adds. list_sum is already under C and Rust (0.73x and 0.72x). A second entry point for fib that skips the callee's `n < 2` test was bounded by hand-writing the source form: 0.120 s to 0.114 s at best, not built.


**Adding in place.** A growing length `n2 = add_checked n, 2` was alive together with `n` (the store at `base + n` comes after the add), so the loop needed two registers and a copy per iteration. `opt/undo.rs`, the last pass of `optimize`, reads `n` after the add as `n2 - 2`: an address takes the `-2` as its displacement, the slow path that grows the buffer gets one `sub`, and the add runs in place on one register (a late pass, because the earlier algebra would fold `(n + 2) - 2` back). strbuild 32.1M to 30.1M instructions, list_sum 110.1M to 100.1M; time about 3% better on both, no other row moved.

**Bounds from the trip count.** An accumulator of a loop that runs a known number of times needs no overflow check when the trip count times its biggest step fits: `n += 2` and `t += n & 7` in a loop of `0..2_000_000` cannot reach `MAX`, and no comparison says so. `ranges.rs` finds loops whose header is `branch (lt c, N)` with `N` constant and a counter that starts at 0 and grows by one on the only way back; a parameter that gains at most `d` per trip is then at most `start + N * d` at the header, and the analysis runs again with that cap. A step that is not one, or a product that passes `MAX`, keeps its check (`accumulators_of_counted_loops_keep_their_traps`). `undo.rs` now also takes the plain `add` that results. strbuild: 30.1M to 20.1M instructions, 10 per iteration, the same as the C loop (20.4M for the whole program).
