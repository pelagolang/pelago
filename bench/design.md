# Benchmarks (draft 2)

Decisions (Dennis, 2026-10-23): benchmark against C **and** C++; against gcc **and** clang (C and C++), plus tcc for the compile-time axis; headline numbers from both a pinned container and a quiet machine; our own program list, grown well beyond goose's 16; target is **at or below the best of all rows**, with Pelago's exact overflow traps on.

## Layout

```
bench/
  design.md            this file: why each program exists, fairness rules
  programs/<name>/     pelago.pel, c.c, cpp.cpp, rs.rs, [cpp-expert.cpp], [sizes.toml], expected*.txt
  harness/run.py       builds, verifies, times, writes results
  toolchains.toml      pinned tool versions (the Dockerfile installs them)
  Dockerfile           the pinned toolchain
  compare.sh           the quick C-and-Rust table that CI runs (compiler/benches/compare.sh forwards to it)
  results/             raw JSON of saved runs (`--save`), one file per date and machine
  results.md           generated by `--save`, never edited by hand
```

## What the harness measures

| Metric | How |
|---|---|
| Run time | median and minimum of N runs after discarded warm-ups; spread = (max-min)/median, rows above 10% are marked `!` |
| Compile time | median of M builds of the same source, source to executable |
| Binary size | file size of the executable |
| Peak memory | Linux: `VmHWM` polled from `/proc` during one extra run (`ru_maxrss` is inflated by the parent Python process); elsewhere `ru_maxrss` |
| Correctness | every executable must print the agreed output (`expected*.txt` if blessed, else the reference row: gcc -O2, clang, g++, rustc), or the row is marked `DIFF` |

Rows: `pelago`, `gcc-O0`, `gcc-O2`, `gcc-O2-trapv`, `clang-O2`, `tcc`, `g++-O2`, `clang++-O2`, `g++-O2-expert`, `rustc-O`, `rustc-O-checked`. Missing compilers drop their rows. `-trapv` and `-checked` are the like-for-like rows with Pelago's overflow checks, and the report has a table of what those checks cost C and Rust. tcc has no optimiser, so it is read on the compile-time table, not as a run-time rival.

## Tiers and fairness rules

- **C**: the plain program, malloc and free by hand.
- **C++ (`cpp.cpp`)**: what a C++ programmer writes first (`vector`, `string`, `unordered_map`, `unique_ptr`, `variant`). On scalar kernels this compiles to the same code as C; it differs where the library matters.
- **C++ expert (`cpp-expert.cpp`)**: hand-built (arena, flat table with inline keys). Only where it changes the result: `bintrees`, `wordfreq`.
- **Rust**: safe, idiomatic code (`Box`, `Vec`, `HashMap`), release mode, one codegen unit.
- Every twin prints the same output; the whole process is timed, so building input and teardown count.
- Sizes: `small` fits in cache, `medium` is the committed source, `large` does not. A twin may only differ in the size literals that `sizes.toml` replaces.
- Representation differences that cannot be removed are named here: in `bintrees` and `interp` Pelago's `enum` with `box` allocates a cell for a leaf where C uses a null pointer.

## Sizes, expected output, results page

- `sizes.toml` in a program directory has `[small]` and `[large]` tables with `replace = [["old", "new"], ...]`, applied to the text of every twin. Programs without one run at medium only (tak, resultpath, structlist, structloop, switchwork).
- `expected.txt` (medium), `expected.small.txt` and `expected.large.txt` are written by `--bless` from the reference row on a machine you trust.
- `--save` writes `results/<date>-<machine>-<os>.json` and `results.md`. `--site FILE` writes the medium results in the `website/content/bench.json` format and `--history FILE` appends one JSON line per run. The `bench-harness` workflow uploads all of them; copying `site-bench.json` to `pelagolang/website` `content/bench.json` is a manual step for now.
- `toolchains.toml` pins versions; the results header says which tools differ.

## First observations (one cloud VM, 1 to 3 runs, not a published result)

- Medium size: Pelago is within about 1.2x of the best other row on `interp` and `wordfreq` and ahead on `mapwork`, but about 2.3x gcc and 7x the arena version on `bintrees`, about 2x on `matmul` and 1.7x on `graph`.
- Large size (cache-busting) is where the gaps open: `mapwork` 8x, `list_sum` 7.6x (growing a 20M-element list), `strsplit` 4.5x, `graph` 3.1x, `blur` 2.9x, `sortwork` 2.5x against the best row. Geometric mean 2.55x, at or below every other row on 2 of 17 programs.
- Six more programs (large, 1 run): `lexer` 5.4x (the `chars()` iterator builds a list of all characters first), `fannkuch` and `lru` about 1.7x, `histogram` 1.4x, `mandelbrot` 1.4x, `crc32` 1.1x.
- So the scalar kernels are close, while memory behaviour (growth, hashing, allocation, cache locality) is the next target. These numbers come from single runs on a shared VM; use them as a pointer, not a result.
